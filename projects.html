Vector Database Benchmarking for HPC

Argonne National Laboratory · Aurora & Polaris

Summer 2026

Research internship, Mathematics & Computer Science Division

The problem. Scientific teams wanted multimodal similarity search at HPC scale, and nobody knew which vector database or index type would hold up — or what each one costs in recall and latency.

What I built. The full evaluation pipeline in Python on Linux: batch job submission on Polaris, dynamic data inserts to test how indexes behave as data grows, and repeatable experiment runs so every before/after comparison was fair. I benchmarked LanceDB, Milvus, and Qdrant across HNSW and IVF indexing, scoring approximate results against brute-force ground truth. Embedding datasets lived on the Eagle and Grand Lustre parallel file systems.

What I learned. IVF recall degraded badly on our fused multimodal embeddings, and my first explanation was wrong. The actual cause was norm asymmetry — embeddings from different modalities had very different magnitudes, which skewed cluster assignment. I corrected the claim in the final report. A benchmark number you can't explain isn't a result yet.

Incremental RAG Pipeline

Distributed & Cloud Computing

CS 441 · UIC

Built across three stages: index, incremental reprocessing, streaming

The problem. Re-embedding an entire corpus every time a few documents change is the default behaviour of most RAG pipelines, and it's wasteful in both compute and storage.

What I built. A distributed ingestion pipeline with content-hash deduplication, so only genuinely changed data gets re-chunked and re-embedded. Incremental, fault-tolerant reprocessing on Spark and Delta Lake, then Flink streaming on AWS EKS for near-real-time index refresh.

What I learned. Deduplication is a correctness problem before it's an efficiency one — getting the hash boundary wrong silently serves stale context to the model, and nothing crashes to tell you.

Explainable Fraud, Waste & Abuse Claim Audit

Machine Learning in Production

CS 544 · UIC

The problem. An insurance claim classifier that flags fraud but can't justify a flag is useless to the auditor who has to act on it.

What I built. A classifier on Databricks where explainability was the actual goal, not a post-hoc add-on. In-depth feature and label importance analysis to show which signals drove each prediction, plus data drift monitoring to catch when incoming claims stopped resembling the training distribution.

What I learned. In production ML, the model is the easy half. Knowing when it has quietly stopped being valid is the hard half.
